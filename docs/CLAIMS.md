# Claims register

Every security-relevant claim this project makes in writing, mapped to the
test that proves it. A claim with no passing test does not belong in the
README, the spec, or a sales conversation. CI runs every proof on every
push (`.github/workflows/ci.yml`).

**Status meanings** — ✅ proven: enforced by a passing test in this repo,
in both implementations where the claim spans both. 📝 specified: written
design, honestly labeled draft; no implementation, therefore no proof yet.
⚠️ known gap: a divergence or limitation we state rather than hide.

## Post-quantum authenticity & confidentiality (0.1, CNSA 2.0 suite)

The 0.1 profile selects its algorithms from the **CNSA 2.0 Category 5** suite:
ML-KEM-1024 (FIPS 203), ML-DSA-87 (FIPS 204), AES-256-GCM, HKDF-SHA-384,
SHA-384. Algorithm selection is an engineering choice, **not a certification** —
see the Disclaimer in the README. Every primitive is implemented in **both**
languages and pinned by a golden vector the TypeScript reference generates and
the Rust crate independently verifies byte-for-byte — the same discipline as
the content-hash vectors above.

## Encrypted transport & key custody

The envelope above (PQ4/PQ7/PQ9) is the confidentiality primitive, proven in both
languages. This section covers the **wiring** that makes what is *sent* ciphertext
by default — the keystore that holds the decryption secret and the transport that
seals/opens with it. These are **TypeScript-only**: the keystore is local custody
that never travels on the wire, and the transport reuses the dual-language envelope,
so neither adds a new cross-implementation contract (if a Rust CLI ever reads the
same keystore file, the blob format becomes a contract that needs its own vector).

| # | Claim | Proof | Status |
|---|---|---|---|
| KS1 | The decryption secret is held only in a passphrase-encrypted keystore (scrypt + AES-256-GCM; it stores seeds, not expanded keys). The stored blob is treated as untrusted: its exact shape and its cost parameters are checked **before** any key derivation (N a power of two from 2¹⁵ to 2²⁰, r = 8, p = 1 — a blob asking for less is refused even with the right passphrase, one asking for more is refused at once), the whole clear header including the org label is authenticated (`sje-keystore/0.2.0`; a 0.1.0 blob still unlocks and is rewritten in the new format at the next save), and wrong passphrase, tampered ciphertext, nonce or header, and a malformed blob all fail with one **uniform** error (no oracle). Unlock re-derives the public key and refuses a substituted identity; one-time prekeys consume exactly once. **Not claimed:** protection against a script running in the page while the keystore is unlocked, or against an older blob being restored (there is no counter). | `src/lib/traveler/keystore.ts`; `keystore.test.ts`; `keys-store.test.ts` | ✅ (TS-only) |

## Honest gaps and drafts

| # | Statement | Where | Status |
|---|---|---|---|
| G1 | Party authentication. 0.0.1 had none — the hash is integrity, not a signature, so any party could claim any `org_id`. 0.1 implements ML-DSA-87 authorship signatures (traveler, quote, and the buyer's award) bound to a signed key directory. | README, SPEC, SECURITY, TRUST | ✅ **resolved in 0.1** (PQ1–PQ6, PQ11). Signature/directory verification lives in the reference library (exercised by the conformance vectors, unit tests, and the soak) **and the browser desk now verifies on receive** — the Authenticity panel on a traveler checks the author, award, and quote signatures against a loaded trust anchor. The desk still never holds **signing** keys and never signs (it does hold its ML-KEM **decryption** secret, but only in a passphrase-encrypted keystore — see G8) |
| G2 | Encrypted envelope (ML-KEM-1024 + HKDF-SHA-384 + AES-256-GCM, algorithms from the CNSA 2.0 Cat 5 suite). 0.0.1 had no confidentiality. | PQ4, PQ7; `docs/ENVELOPE-DRAFT.md` | ✅ **resolved in 0.1** with the dual-language golden vectors the draft itself demanded |
| G3 | TS parse (zod) and the Rust structural parse now accept and reject the same documents. The former acceptance gap — Rust accepting documents zod refused (looser numeric ceilings, missing string/count bounds, unknown keys, lenient datetimes) — is closed by a full structural validator in the Rust core. A follow-up closed the remaining **two-way** divergences at the parse boundary where zod and serde differ by default (`de.rs`): the Rust core now **accepts** an integer-valued float (`250.0`) into an integer field as zod does, and **refuses** an explicit `null` on a non-nullable optional as zod does. A further hardening pass aligned three more parse-boundary details: string-length bounds count **code points** (zod v4 semantics) rather than UTF-16 units, a **non-finite** number is refused on both, and both honor the same **128-container** nesting limit. | this file (C12–C14); `crates/secure-job-envelope/src/{validate,de}.rs`; the differential + committed corpus (C15) | ✅ **resolved in this pass** — a seeded TS↔Rust differential over thousands of documents finds zero accept/reject divergence, pinned by shared reject vectors and the committed corpus |
| G6 | The 512 KiB size limit used to be measured on the raw input length in Rust but on the re-serialized (compact, **UTF-16**) length in zod — which was not the "negligible edge" this row once called it: a document of CJK text is three UTF-8 bytes per UTF-16 unit, so TypeScript accepted (and would sign) travelers up to ~1.5 MB that the Rust core refused. Both sides now measure **UTF-8 bytes of the wire text**; a value with no text (an API argument) is measured by its compact serialization. | SPEC §Parsing rule 8; `wire.ts`, `conformance.ts::parseTravelerJson`; `lib.rs::parse_traveler`; `wire.test.ts` (a document under 512 Ki UTF-16 units and over 512 KiB of UTF-8 is refused on every entry point) | ✅ **resolved** (C14) |
| G4 | Forward secrecy. The base 0.1 envelope encapsulates only to a recipient's **static** ML-KEM key (a later compromise exposes past envelopes). | G5 | Key sorting for non-ASCII keys now uses Unicode code point order on both sides (== UTF-8 byte order), so astral-plane keys sort identically; field names remain ASCII regardless. | SPEC §Canonical JSON; C1 | ✅ **resolved** — `canonical.ts` code-point sort; vector `astral-key-order` (both runners) |
| G7 | Archive integrity is **unkeyed** SHA-384: the required `traveler_json_sha384` digest refuses any byte-level tamper of a received archive (award/ship_to/ops included), but a party that re-seals an archive recomputes the digest, so adversarial authenticity rests on the ML-DSA signature layer. The buyer now signs **both** the quoteable body (PQ3) **and** the award — the award decision + ship-to, additionally binding the awarded quote's priced content via `quote_hash` (PQ11) — so the business-email-compromise case (a forged award or redirected ship-to sealed to the winner by a non-buyer) is refused on both implementations, as is a swapped price on the awarded quote. | G8 | Key-custody posture reversal. The desk now holds its ML-KEM **decryption** secret, in a passphrase-encrypted keystore (encrypted at rest; plaintext in memory only while unlocked). It does **not** protect against script in the origin — an XSS on an **unlocked** desk can read the in-memory secret (ML-KEM runs in JS; the key is extractable during decapsulation). The desk still never holds **signing** keys. | G9 | Duplicate JSON object keys. This row previously argued the split was "not exploitable" and deferred it. That argument was wrong in one respect that matters: a last-wins parser never *examines* the value it discards, so a duplicate could hide content from every check on one side (an out-of-range number, a second `award`) that the other side read. | G10 | ~~The 8 KiB blob size cap (`assumptions` / `capacity` / `as_built`) is measured on `JSON.stringify(v).length` in zod vs `serde_json::to_string(v)` length in Rust.~~ **Resolved.** This row called the edge "negligible" and said aligning it "would mean reimplementing JS number rendering in Rust". The audit measured it by hand and the byte-level fuzzer found it unaided in its first run (a blob of 431 numbers written `1e15`: accepted by TypeScript, refused by Rust; 373 written `1e20`: the reverse), and no reimplementation was needed: the cap is now defined on the canonical form, which both sides already produce byte for byte, in UTF-8 bytes (SPEC, parsing rule 12). ## Running the proofs

```bash
npm test                                # TS: vectors + traveler suite + store state machine
cd crates/secure-job-envelope && cargo test   # Rust: unit + golden + shared vectors + fuzz corpus replay
node --experimental-strip-types conformance/generate.ts   # regenerate vectors (TS is generator, Rust is independent verifier)

# Cross-implementation hardening (the crossimpl CI job runs all three):
cargo build --release --manifest-path crates/secure-job-envelope/Cargo.toml  # the differential's other half
npm run soak                            # simulate + transact hundreds of jobs, assert lifecycle invariants
npm run differential                    # seeded TS<->Rust differential fuzz (parse/hash/level/bound)
npm run corpus                          # regenerate the committed cross-impl fuzz corpus (conformance/fuzz)
```
